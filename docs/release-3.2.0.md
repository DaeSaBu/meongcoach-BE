# 3.2.0 서버 배포와 구버전 앱 지원

앱 3.0.0·3.1.0과 3.2.0은 같은 운영 서버와 같은 DB를 사용한다. 구버전 요청도 새 서버가 새 스키마에 저장한다. 심사 승인 시점과 DB 전환 시점을 맞출 필요는 없다. 호환 서버 배포와 운영 확인을 마친 뒤 3.2.0을 심사에 제출한다.

## 유지하는 API 계약

| 기능 | 구버전 앱 | 3.2.0 앱 | 서버 처리 |
|---|---|---|---|
| 온보딩 메타데이터 | MBTI·교육 토픽 사용 | 견종·성격 사용 | `mbtis`·`topics`·`breeds`·`personalities` 모두 반환 |
| 온보딩 완료 | 보호자 정보·몸무게·기대 사항 포함 | 강아지 정보만 전송 | 보낸 값은 저장하고 생략한 값은 기본값 사용 |
| 강아지 수 | 최대 5마리 | 1마리 | 1~5마리 허용 |
| 강아지 이름 | 3.0.0은 최대 50자 | 최대 12자 | 온보딩·등록·수정 모두 최대 50자 허용 |
| 온보딩 사진 | `target: USER_PROFILE / DOG_PROFILE` | target 생략 | 명시한 대상에 발급, 생략하면 강아지 사진 |
| 기존 강아지 사진 | 저장된 URL을 수정 요청에 재전송 | 동일 | 소유 강아지의 기존 URL은 유지 가능, 바뀐 URL만 경로·소유자 검증 |

생년월일은 3.0.0·3.1.0 화면에서도 필수다. 서버의 과거 날짜 필수 검증은 유지한다. 온보딩 보호자 정보는 구버전에서 사용하므로, 3.2.0 앱이 쓰지 않는다는 이유로 버리지 않는다.

새 앱 기능인 맞춤 플랜·실습 인증 등의 API는 새 서버를 필요로 한다. 구버전 지원 종료와 DB 전환은 별개이며, 이번 배포에서 최소 앱 버전을 3.2.0으로 올리지 않는다. 플랫폼별 스토어에서 업데이트를 실제로 받을 수 있기 전에는 해당 버전으로 강제 업데이트하지 않는다.

## DB 전환 방식

V22는 `user_profiles.user_id`를 제거하고 `users.profile_id`로 연결한다. V23은 `topic_progress`를 `topic_selection`으로 바꾼다. 기존 서버가 실행 중일 때 새 서버가 이 마이그레이션을 적용하면 구 서버의 조회가 실패한다. 이번 전환은 구 서버를 모두 멈춘 상태에서 진행한다. V1~V34 파일은 이미 dev에 적용됐으므로 수정하거나 Flyway 이력을 지우지 않는다.

현재 `cd-prod.yml`은 main push 시 롤링 배포한다. **이번 스키마 전환에 그 자동 배포를 그대로 사용하지 않는다.** 이 PR은 CD 동작을 변경하지 않는다. 아래는 담당자가 수행하는 수동 점검 배포 절차이며, 아직 운영에 실행한 작업이 아니다.

### 점검 전에 준비

1. 개발 서버에서 구버전과 3.2.0의 가입·로그인·강아지 수정·훈련 완료, 3.2.0의 플랜 생성·완료를 확인한다. 사진이 있는 구버전 가입과 여러 마리 가입도 포함한다.
2. **릴리스 PR을 main에 머지하기 전에** GitHub Actions의 `CD - Prod`를 비활성화하고 진행 중인 운영 CD가 없는지 확인한다. CI 검사를 통과한 릴리스 커밋을 확정하고, 해당 커밋의 `bootJar`와 ECR 이미지를 미리 준비한다. 점검 중에 테스트·이미지 빌드를 시작하지 않는다.
3. 현재 ECS 서비스 `meongcoach-prod-cluster / meongcoach-prod-svc`의 태스크 정의 ARN·이미지 SHA·desired count·자동 확장 및 배포 설정을 기록한다. 새 태스크 정의는 현재 운영 리비전을 복제해 `api` 컨테이너 이미지와 `SENTRY_RELEASE`를 확정한 커밋으로 변경한다. DB 연결·시크릿·최소 앱 버전은 기존 운영 값을 유지한다. 등록만 하고 서비스에는 아직 적용하지 않는다.
4. 운영 DB 백업·복원 경로와 권한을 확인하고, 스냅샷 복원에 필요한 시간을 사전에 측정한다. 최신 백업이라는 표시만으로 복구 시간을 추정하지 않는다. 점검 종료 예정 시간은 전환·검증·복원 리허설 결과로 정한다.
5. 기존 프로필 수·회원 연결, 강아지 수, 선택 토픽·학습 횟수와 Flyway 적용 버전을 기록한다. V16 이후 예상하지 못한 운영 변경이 있으면 비교 기준부터 다시 확인한다.
6. 아래 조건부 데이터 문제도 확인한다. 커뮤니티 본문 제한 초과 데이터가 있으면 별도 보존·전환 방안을 정하며, 사용자 본문을 임의로 잘라내지 않는다. 이 PR은 커뮤니티 본문 제한 변경을 되돌리지 않는다.

```sql
SELECT id, char_length(content) FROM posts WHERE char_length(content) > 200;
-- 운영에 comments 테이블이 이미 있는 경우에만 실행
SELECT id, char_length(content) FROM comments WHERE char_length(content) > 150;
```

### 점검 시작부터 서비스 재개까지

1. 이용자가 적고 담당자가 즉시 대응할 수 있는 시간에 점검을 시작한다. 외부 진입점에서 일반 요청을 점검 응답(503)으로 전환하고 진행 중인 요청을 정리한다. 실제 라우팅 장비와 점검 응답 설정은 운영 담당자가 배포 전에 확인해야 한다. API health 하나만 확인하고 점검을 해제하지 않는다.
2. ECS 자동 확장·예약 확장을 중지해 태스크가 다시 늘어나지 않도록 한다. ECS circuit breaker·CloudWatch 배포 알람의 **자동 롤백도 해제**한다. 마이그레이션 이후 예전 이미지만 자동 복원하면 구 스키마 조회가 실패하기 때문이다. 변경 전 설정은 기록한다.
3. 서비스 desired count를 0으로 낮춘다. 기존 태스크 전부의 `lastStatus`가 `STOPPED`가 될 때까지 기다린다. running count가 0인 것만으로 프로세스 종료를 판단하지 않는다. 같은 DB에 쓰는 별도 워커·관리자 작업이 있으면 함께 멈춘다. SQS 처리 중 작업은 종료 유예 시간과 재처리 가능 여부를 확인한다.
4. 쓰기가 멈춘 상태의 DB 백업을 생성하고 완료를 확인한다. 이 시점과 기존 태스크 정의를 복구 기준으로 기록한다.
5. 새 태스크 정의를 서비스에 적용하고, 우선 새 태스크 1개만 시작한다. 새 서버가 Flyway 마이그레이션을 실행한다. 로그에서 V17~V34 적용·JPA 스키마 검증·서버 시작을 확인한다. 구 서버를 함께 올리지 않는다.
6. 점검 응답을 유지한 채 담당자 접근 경로로 새 서버를 검증한다. 프로필 연결과 학습 이력이 보존됐는지, 구버전 신규 가입·기존 계정 로그인·강아지 수정·훈련 완료가 되는지 확인한다. 3.2.0 온보딩과 맞춤 플랜도 확인한다. 테스트 데이터는 식별해 정리한다.
7. 새 태스크만으로 원래 desired count를 복구하고 안정화한 뒤 일반 요청을 다시 연다. 새 서버 오류와 DB 오류를 확인한다. 자동 확장 설정을 복원한다. 자동 롤백은 되돌아갈 리비전이 새 스키마와 호환되는지 확인한 후에만 복원한다.
8. GitHub의 `CD - Prod`를 다시 활성화한다. 이미 끝난 이번 배포를 기존 main CD로 재실행하지 않는다. 수동 배포한 SHA·태스크 정의·DB 버전·검증 결과를 릴리스 기록에 남긴다. 이후 자동 배포도 DB 변경이 구 서버와 호환되는지 먼저 확인한다.

### 실패 시 복구

- 새 서버를 한 번이라도 실행했다면 Flyway 버전을 먼저 확인한다. 서버 시작 실패가 DB 미변경을 뜻하지 않는다.
- 마이그레이션 전 실패라면 이전 태스크 정의와 desired count를 복구하고 검증한 뒤 점검을 해제할 수 있다.
- 마이그레이션 후 실패라면 점검을 유지한다. 새 스키마에 맞는 수정 서버를 배포하거나, 모든 DB 쓰기 주체를 멈춘 채 4단계 백업을 복원한 DB와 이전 태스크 정의를 함께 사용한다. 이전 이미지만 다시 올리지 않는다.
- 트래픽을 재개한 뒤 백업을 복원하면 재개 이후 데이터가 사라질 수 있다. 이때는 자동 복원하지 않고 새로 생긴 데이터를 보존·재반영하는 별도 복구 계획을 세운다.

## 검증 범위

`OnboardingControllerTest`·`OnboardingCompleterTest`는 구·신 요청 수신과 실제 저장을 검증한다. `OnboardingMetadataFinderTest`는 구버전 선택 목록을, `OnboardingImageUploadUrlIssuerTest`는 두 사진 경로를 검증한다. `DogControllerTest`·`DogRegisterProfileUpdateTest`는 이름 길이와 기존 사진 보존을 검증한다.

`LegacyProfileMigrationTest`는 V16 운영 스키마에 서로 다른 회원 프로필을 넣고 최신 마이그레이션 후 같은 회원으로 연결되는지 확인한다. `ProgressMigrationTest`는 토픽 선택과 학습 횟수 보존을, `FlywaySchemaValidationTest`는 최종 스키마와 엔티티의 일치를 검증한다. 이 자동 검증은 운영 DB 백업·복원 리허설과 실기기 확인을 대체하지 않는다.
