# Linear 컨벤션

이 저장소의 작업은 Linear 티켓 하나에서 시작한다. 에이전트는 Linear MCP 도구(`list_issues`, `get_issue`, `save_issue`, `list_cycles`)로 티켓을 다룬다. MCP 서버 이름은 작업자 환경마다 다르므로 도구는 동작 이름으로 찾는다.

---

## 작업 시작 절차

코드를 고치기 전에 다음 순서를 따른다.

1. 맡은 작업의 티켓을 찾는다. ([티켓 찾기](#티켓-찾기))
2. 티켓이 있으면 그 티켓으로 작업하고, 없으면 만든다. ([티켓 만들기](#티켓-만들기))
3. 티켓 상태가 `Backlog`·`Todo`면 `In Progress`로 바꾼다. ([상태](#상태))
4. 티켓 번호로 브랜치를 만든다. 브랜치 이름·분기 기준·PR 규칙은 [git-convention 스킬](../git-convention/SKILL.md)의 "브랜치 규칙"을 따른다.

작업자가 `DAE-123`처럼 번호를 알려 주면 검색하지 않고 `get_issue`로 그 티켓을 읽는다.

---

## 티켓 찾기

- `list_issues`의 `query`로 제목·본문을 검색한다. 한 번에 한 낱말만 넣고, 낱말을 바꿔 여러 번 검색한다.
	- 기능의 한글 이름, 영문 용어, 기능이 속한 모듈 이름을 각각 검색한다. (예: 신고 기능 → `신고`, `report`, `커뮤니티`)
- 상태 필터를 걸지 않는다. `Done`·`Canceled` 티켓이 나오면 이미 끝냈거나 그만둔 작업이므로, 새 티켓을 만들기 전에 작업자에게 알린다.
- 티켓은 프론트엔드와 백엔드가 한 팀에서 함께 쓴다. 같은 기능의 앱 티켓만 있고 백엔드 티켓이 없으면 백엔드 티켓을 따로 만든다.
- 후보가 여럿이거나 범위가 일부만 겹치면 고르지 않고 작업자에게 묻는다.

---

## 티켓 만들기

`save_issue`를 `id` 없이 호출한다. 값은 다음을 기본으로 한다.

| 항목 | 값 |
|---|---|
| `team` | `DaeSaBu` (키 `DAE`) |
| `project` | 기능 개발은 `개발`, 운영 중인 기능의 오류 수정은 `핫픽스` |
| `assignee` | `me` |
| `cycle` | 현재 사이클 번호. `list_cycles`를 `type: current`로 호출해 얻는다 |
| `priority` | `3` (Medium) |
| `state` | 바로 시작하면 `In Progress`, 나중에 할 일이면 `Backlog` |

### 제목

- 무엇을 만드는지 한 문장으로 쓰고 `구현`, `추가`, `수정`, `제거`처럼 명사형으로 끝낸다.
- 서버 작업이면 제목에 `백엔드`를 넣어 앱 티켓과 구분한다. (예: `AI 분석 구매 횟수를 RevenueCat 잔액과 동기화하는 백엔드 API 구현`)

### 본문

읽는 사람은 기획·프론트엔드 팀원이다. 클래스 이름과 파일 목록 대신 API 경로·응답·에러 코드처럼 밖에서 보이는 것을 쓴다.

```markdown
## 개요

왜 필요한지와 무엇을 하는지 두세 문장.

## 범위

* 추가·변경하는 API, 테이블, 문서
* 이 티켓에 넣지 않는 것이 있으면 따로 밝힌다

## 인수 조건

- [ ] 사용자나 앱이 확인할 수 있는 결과 한 줄씩

## 배포 전 확인

* 환경 변수, 마이그레이션, 앱 출시 순서처럼 배포할 때 챙길 것
```

- `배포 전 확인`은 챙길 것이 없으면 뺀다.
- 본문의 줄바꿈은 `\n` 문자열이 아니라 실제 줄바꿈으로 보낸다.

---

## 상태

- 에이전트가 직접 바꾸는 상태는 `In Progress` 하나다. 바꾸기 전에 `get_issue`로 현재 상태를 읽고, 이미 `In Progress` 이후 상태면 그대로 둔다.
- `In Review`와 `Done`은 직접 바꾸지 않는다. Linear의 GitHub 연동이 PR에 맞춰 옮긴다 — draft를 해제하면 `In Review`, 머지되면 `Done`.
- 연동은 브랜치 이름의 이슈번호로 PR과 티켓을 잇는다. PR을 만든 뒤 티켓의 `attachments`에 PR이 붙었는지 `get_issue`로 확인한다.
- 작업 중에 범위가 바뀌면 티켓 본문의 `범위`와 `인수 조건`을 고친다. 본문 일부만 고칠 때는 `save_issue`의 `patch`를 쓴다.
